# Compliance scans on the certified substrate — 2026-08-16

Gathered while the SLES eval subscription is active (expires 2026-10-14). Substrate: 3-node
SLES 15 SP7 + RKE2 v1.35.7 + FIPS mode (all nodes `fips_enabled=1`, crypto packages version-locked).
Scans run on chaos-node-3 (representative — all 3 nodes are provisioned identically from one AutoYaST
profile). These are **dated compliance-posture snapshots of the substrate**, not a certification of
open-infra; they show the substrate is scannable/hardenable to recognized baselines and is FIPS-clean.

- This is the **as-provisioned baseline** — open-infra's AutoYaST installs a minimal server + FIPS, it
  does NOT apply full STIG hardening. Per the inheritance model, STIG hardening (audit rules, password
  policy, mount options, login banners, service minimization) is the **deployer's** responsibility.
- **FIPS-mode STIG rules PASS** (`is_fips_mode_enabled`, FIPS-validated ciphers/KEX/MACs) — the
  load-bearing crypto controls are already met.
- Remediation path is documented, not guessed: `stig-remediation.sh` (generated by
  `oscap xccdf generate fix`, ~30k lines) is the exact bash to close the 154 fails. NOT applied here
  (full STIG remediation changes sysctl/mounts/services and can interfere with Kubernetes — it belongs
  to the deployer's hardened image, and would want a remediate-then-rescan pass under test).
- Other baselines are available in the same SCAP guide if needed: PCI-DSS v4, HIPAA, ANSSI-BP-028.

## Honest framing
These scans make the point-in-time validation **assessor-legible**: the OS was DISA-STIG-scanned and
the Kubernetes distro CIS-benchmarked, both under FIPS mode, on a subscribed/certified substrate, with
a documented remediation path and enforced crypto version-locks. What they do NOT claim: that the
substrate is *STIG-compliant as shipped* (it is a baseline needing deployer hardening) or that
open-infra itself is certified (the CC/FIPS evaluations cover the OS + Kubernetes crypto module).

## STIG remediation feasibility on a Kubernetes node (analysis, not applied)
Applying the full `stig-remediation.sh` to a running RKE2 node would **break the cluster** — a known
DISA-STIG-vs-container-platform tension. Categorizing the 154 STIG fails from our scan:

**~15 controls are Kubernetes-incompatible** (must be excluded via a tailored STIG profile):
- `sysctl_net_ipv4_ip_forward` — STIG requires IP forwarding **off**; Kubernetes pod networking requires it **on**. (Hard conflict.)
- `sysctl_net_ipv4_conf_*_send_redirects`, `*_accept_source_route`, `*_forwarding` — CNI/routing sysctls.
- `service_firewalld_enabled` — STIG wants the host firewall enabled; we disabled firewalld so RKE2/Canal ports form (finding D5). A deployer would instead open the RKE2 ports in firewalld.
- `mount_option_home_nosuid`, `partition_for_var_log_audit`, a couple mount/partition rules — can perturb the container runtime / require partitioning the image.

**~140 controls are safely remediable** on a k8s node (the deployer's hardened image applies these):
- The large `audit_rules_*` set (DAC modifications, privileged commands), password policy
  (`accounts_password_set_{max,min}_life`, `pam_faildelay`), `umask`, login banners, PAM, file
  permissions, AIDE (`aide_*`).

**Achievable STIG posture** ≈ the 63 already-passing + ~140 safely-remediable ≈ **~200 / 217 applicable**,
with ~15 documented, expected k8s exceptions. This is the honest hardening story: the substrate is
substantially STIG-hardenable, and the residual exceptions are inherent to running Kubernetes (they'd
be captured as tailoring justifications in a real ATO package), NOT open-infra gaps.
